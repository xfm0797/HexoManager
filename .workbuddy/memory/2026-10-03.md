## 修复「文章管理 → 编辑区一直 loading，预览正常」（Monaco CDN 被 CSP 拦截）

**现象**：文章管理页右侧编辑区永久 loading；同页 Markdown 预览正常。

**根因（三层因果，已用独立脚本复现）**：
1. 编辑区用 `@monaco-editor/react`，其底层 `@monaco-editor/loader` 默认从
   `https://cdn.jsdelivr.net/npm/monaco-editor@0.55.1/min/vs` 动态注入 `<script>` 加载 Monaco；
2. `src-tauri/tauri.conf.json` 的 CSP 为 `script-src 'self'`，外链脚本被 WebView 拦截
   → loader 的 Promise 永不 resolve → `<Editor>` 永久停留在默认 loading；
3. 预览用的是随产物打包的 `react-markdown`，同源渲染 → 正常（这解释了"预览正常"的差异）。

**修复**：
- 新增 `src/utils/monaco.ts`：`loader.config({ monaco })` 指向本地打包实例 + 配置
  `MonacoEnvironment.getWorker`（editor/json/css/html/ts 五个 worker）；
- `src/main.tsx` 顶部以副作用方式 `import '@/utils/monaco'`，先于任何编辑器渲染。

**关键坑（务必记住）**：`monaco-editor@0.57` 的 `package.json exports` 把子路径映射为
`./esm/vs/*.js`，因此 worker 必须写成
`monaco-editor/<lang>/<name>.worker.js?worker`（**去掉 `esm/vs/` 前缀、保留 `.js`**）。
旧写法 `monaco-editor/esm/vs/.../x.worker?worker` 会 Rollup 解析失败。

**验证**：
- 独立复现脚本 `.repro/monaco-cdn-repro.mjs`：修复前"BUG 复现成功"，修复后"未复现"；
- `tsc --noEmit` 通过；
- `vite build` 成功，产物含 5 个 worker chunk + `MonacoEnvironment`，monaco chunk ≈ 4MB。

**环境备注**：`npm ci` 因 esbuild 的 postinstall 失败（缺 `@esbuild/win32-x64`）中断，
补装 `npm install --no-save --package-lock=false @esbuild/win32-x64@0.21.5` 后恢复正常，
未改动 `package.json`/`package-lock.json`。

**已提交**：`d0a0437 fix: 修复 Monaco 编辑器从 CDN 加载被 CSP 拦截导致编辑区永久 loading`

## 本地构建打包排障（Windows）

### 障碍一：沙箱批量删除保护拦截 vite 清理 dist
- 现象：`npm run tauri:build` → beforeBuildCommand（vite build）在 `prepareOutDir` 处失败，
  报 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":103,"threshold":50,...}`
- 原因：WorkBuddy 环境的 node-safe-delete-shim 拦截单次删除 >50 个文件的 rmSync；
  离屏时 bash 的 `rm -rf dist` 也会被拦（即便用 `run_in_background` 也无法弹窗授权）
- 解法：**先在前台单独执行 `rm -rf dist`**（会走授权），再启动构建；不要把清理与构建串在一条后台命令里
- 注意：前端类型检查位于 `npm run build`，而 tauri 的 beforeBuildCommand 用的是 `build:only`（不含 tsc）

### 障碍二：schemars E0107 —— 本机 autocfg 探测失败（已用独立复现程序定位到根因）
- 现象：`cargo` 编译 `schemars` 报 `E0107: struct takes 3 generic arguments but 2 were supplied`
  （`schemars-0.8.22/src/lib.rs:12 pub type Map<K, V> = indexmap::IndexMap<K, V>;` vs `indexmap 1.9.3`）
- **完整因果链（逐环验证）**：
  1. `tauri-build 2.7.0/2.7.1`、`tauri-plugin 2.7.x` 声明 `schemars` 的 `preserve_order` 特性；
  2. schemars 0.8.22 的 `preserve_order = ["indexmap"]` 指向 **indexmap 1.x**；
  3. indexmap 1.9.3 的 `IndexMap` 只在 `#[cfg(has_std)]` 分支才有默认泛型参数
     （`pub struct IndexMap<K, V, S = RandomState>`），`not(has_std)` 分支是 `IndexMap<K, V, S>`；
  4. indexmap 1.9.3 **没有 `default = ["std"]`**，而 schemars 只启用 `serde-1`
     → 编译期 `CARGO_FEATURE_STD` 为空 → 其 build.rs 走 autocfg 的
     `emit_sysroot_crate("std")` 探测分支；
  5. **本机该探测失败**：autocfg 的探测要 spawn rustc 并用管道传源码/输出，本机报
     `Os { code: 231 } 所有的管道范例都在使用中`（Windows ERROR_PIPE_BUSY），autocfg 只能
     打印 `could not probe for `std`` 并放弃 → `has_std` 未置位 → E0107
- 复现方式：`.repro/autocfg-probe`（最小 crate，build.rs 复刻 indexmap 的调用）
  → `probe_sysroot_crate(std)=false`；按 autocfg 参数精确复刻后拿到上面的 pipe-busy 报错。
  **沙箱外重跑同样失败** → 是本机环境问题，与 AI 沙箱无关
- 反证：GitHub Windows 运行器上同一份 lock **编译成功**（v1.0.2 已产出 msi/nsis/sig）
  → 该阻塞**只出现在本机**，CI 不需要此补丁
- 解法（本机绕过）：vendor 补丁 —— `src-tauri/patches/schemars-0.8.22/`，三处改动
  1. `Cargo.toml`：`preserve_order = ["indexmap2"]`
  2. `src/lib.rs`：`Map` → `indexmap2::IndexMap<K, V>`
  3. `src/lib.rs`：`MapEntry` → `indexmap2::map::Entry<'a, K, V>`
  并在 `src-tauri/Cargo.toml` 加 `[patch.crates-io] schemars = { path = "patches/schemars-0.8.22" }`
  （补丁后 indexmap 1.9.3 完全退出依赖图，`cargo tree -i indexmap@1.9.3` 为空）
- 上游若有修复（schemars 0.8.23+ 或 tauri-build 换掉 preserve_order），应移除该补丁
